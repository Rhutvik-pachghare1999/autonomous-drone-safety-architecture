# WCET Benchmark — Methodology and Evidence

This document describes exactly how the HOCBF filter latency numbers were
produced, what the committed raw data contains, and what a fresh clone can and
cannot reproduce.

## What is measured

`src/rt/safety_filter.c` times the `hocbf_filter()` hot path with
`clock_gettime(CLOCK_MONOTONIC_RAW)` around each call, for N trials, and writes
every sample to `experiments/results/latency_raw.csv`
(columns: `trial,latency_ns,jitter_ns`).

`hocbf_filter()` is a closed-form clamp: a handful of double-precision
arithmetic operations, one `cos`, one `sin`, no heap allocation and no system
calls. See `src/rt/safety_filter.c` lines 64–77.

## Committed raw data

`experiments/results/latency_raw.csv` (100,000 rows, ~1.1 MB) is committed as
the raw evidence behind the WCET number. Summary of that file:

| Metric | Value (ns) |
|--------|-----------|
| min    | 20        |
| mean   | 22.31     |
| p50    | 20        |
| p99    | 31        |
| p99.9  | 31        |
| **max (WCET)** | **2,725** |

These match `experiments/results/wcet_evt.json`, which is regenerated by
`experiments/exp_wcet_evt.py` from this CSV.

## Two different runs — do not conflate them

### 1. Local RT run (source of the committed 2,725 ns)

The committed CSV was produced by the author on a Linux laptop
(AMD Ryzen 7 5800H, as recorded in the `safety_filter.c` header) under
real-time scheduling:

- `SCHED_FIFO` priority 99
- pinned to CPU core 2
- `mlockall(MCL_CURRENT | MCL_FUTURE)`

```bash
gcc -O3 -march=native -DNO_ONNX -o build/safety_filter src/rt/safety_filter.c -lm -lrt
sudo ./build/safety_filter 100000 2      # 100k trials, core 2; sudo needed for SCHED_FIFO + mlockall
```

The 2,725 ns worst case is a **single outlier** across 100k samples — the p99
is 31 ns. The outlier is consistent with a rare OS interrupt on a stock
(non-PREEMPT_RT) kernel. `exp_wcet_evt.py` fits a Gumbel tail (block maxima) and
extrapolates a p=1e-9 bound of ~1,733 ns.

### 2. Standard fresh-clone run (no root, no RT scheduling)

Without `sudo`, `sched_setscheduler` and `mlockall` fail (the program prints a
`perror` warning and continues), so you measure the arithmetic cost without RT
isolation:

```bash
gcc -O3 -DNO_ONNX -o build/safety_filter src/rt/safety_filter.c -lm -lrt
./build/safety_filter 1000 0
```

A representative fresh-clone run on the same class of machine (no `-march=native`,
no RT, 1,000 trials) observed **p99 = 30 ns, WCET = 31 ns** — i.e. the arithmetic
is fast and stable; the 2,725 ns tail comes from the OS scheduler under the RT
run, not from the filter itself.

## Reproducibility limits

- The exact 2,725 ns tail depends on the specific machine, kernel, and system
  load at capture time. It will not reproduce sample-for-sample. The committed
  CSV is the artifact of record.
- `-march=native` targets the build host's CPU. It is a desktop convenience,
  not an embedded-target build. Cross-compilation for a flight-controller CPU
  is future work (see README "Limitations").
